## .gitignore Explained in Plain Words

### **1. Byte-compiled / Optimized / DLL Files**
```
__pycache__/
*.py[cod]
*$py.class
```
**What they are:** When Python runs your code, it creates compiled versions (`.pyc`, `.pyo`, `.pyd` files) in `__pycache__` folders for faster execution. These are temporary and specific to your machine.

**Why ignore them:** They're auto-generated and different for each computer. Sharing them causes conflicts. Python will regenerate them automatically when needed.

**For your project:** When you run scrapers, Python will create these files. Git should ignore them.

---

### **2. C Extensions**
```
*.so
```
**What they are:** `.so` files (shared objects) are compiled C/C++ libraries used by Python packages like numpy or pandas.

**Why ignore them:** They're platform-specific (different for Linux, Mac, Windows) and auto-generated by build processes.

**For your project:** If you use libraries like BeautifulSoup4 (for scraping), they may have compiled extensions. Don't commit them.

---

### **3. Distribution / Packaging**
```
build/
develop-eggs/
dist/
downloads/
eggs/
.eggs/
lib/
lib64/
parts/
sdist/
var/
wheels/
*.egg-info/
.installed.cfg
*.egg
MANIFEST
```
**What they are:** When you package your project (using `setup.py` or `pip install -e .`), Python creates these directories and files with build artifacts, distribution packages, and installation info.

**Why ignore them:** These are generated during the build/install process and should never be in source control. Each developer rebuilds them locally.

**For your project:** When you create a distributable package for pip, ignore these. Users will regenerate them on their machines.

---

### **4. PyInstaller**
```
*.manifest
*.spec
```
**What they are:** PyInstaller is a tool that converts Python scripts into standalone executables. These files are its build configuration and output.

**Why ignore them:** These are build artifacts, not source code.

**For your project:** If you eventually want to bundle your product finder as a `.exe` or standalone app, ignore these build files.

---

### **5. Installer Logs**
```
pip-log.txt
pip-delete-this-directory.txt
```
**What they are:** Log files created when pip (Python's package manager) installs or uninstalls packages. They contain error messages and installation details.

**Why ignore them:** They're temporary debugging info specific to each machine's install session.

**For your project:** When team members run `pip install -r requirements.txt`, they'll generate these. Don't commit them.

---

### **6. Unit Test / Coverage Reports**
```
htmlcov/
.tox/
.nox/
.coverage
.coverage.*
.cache
nosetests.xml
coverage.xml
*.cover
*.py,cover
.hypothesis/
.pytest_cache/
```
**What they are:** When you run tests (using pytest or similar), these files track code coverage (what % of your code is tested), test results, and caching.

**Why ignore them:** Test results are specific to each run and each developer's environment. You want fresh test runs, not cached old results.

**For your project:** When you write tests for your scrapers and processors, run them locally but don't commit the reports.

---

### **7. Django / Flask**
```
*.log
local_settings.py
db.sqlite3
db.sqlite3-journal
instance/
.webassets-cache
```
**What they are:** Log files and database files from web frameworks. `local_settings.py` contains local configuration overrides.

**Why ignore them:** Database files change constantly during development. Local settings have secrets (API keys, passwords). Log files are temporary debugging info.

**For your project:** If you add a web interface (Django/Flask) later, these files will contain secrets and shouldn't be committed.

---

### **8. Scrapy Stuff**
```
.scrapy
```
**What they are:** Configuration and cache directory for Scrapy (a web scraping framework).

**Why ignore them:** Local scraper cache and settings specific to your machine.

**For your project:** If you use Scrapy for web scraping instead of BeautifulSoup4, this will store temporary data. Ignore it.

---

### **9. Sphinx Documentation**
```
docs/_build/
```
**What they are:** When you generate HTML documentation from your Python docstrings using Sphinx, it creates this folder with the built HTML.

**Why ignore them:** This is generated output; the source docstrings are in your `.py` files.

**For your project:** When you document your scrapers and API, ignore the built docs.

---

### **10. Virtual Environments** ⭐ **CRITICAL FOR SECRETS**
```
.env
.venv
env/
venv/
ENV/
env.bak/
venv.bak/
```
**What they are:** Virtual environments are isolated Python installations with project-specific packages. The `.env` file stores environment variables.

**Why ignore them:** 
- Virtual environments are 100s of MB and specific to your machine
- `.env` files often contain secrets like API keys, database passwords, and credentials
- Each developer creates their own virtual environment locally

**For your project:** 🔴 **CRITICAL** — Your `.env` file will contain:
  - API keys for retail websites
  - Database credentials
  - Authentication tokens
  
If you accidentally commit this, hackers can use your credentials to impersonate you!

**Best practice:** Create `.env.example` with dummy values and commit that instead.

---

### **11. IDE and Editor Settings** ⭐ **IMPORTANT**
```
.vscode/
.idea/
*.swp
*.swo
*~
.DS_Store
```
**What they are:**
- `.vscode/` — Visual Studio Code settings and extensions
- `.idea/` — JetBrains IDEs (PyCharm, IntelliJ) settings
- `*.swp`, `*.swo`, `*~` — Vim/Nano temporary edit files
- `.DS_Store` — macOS folder metadata

**Why ignore them:** Each developer has different IDE settings and preferences. Committing these causes merge conflicts.

**For your project:** Different team members might use PyCharm vs VS Code. Don't force one IDE's settings on everyone.

---

### **12. Project-Specific Secrets** ⭐⭐ **MOST CRITICAL FOR YOU**
```
config/secrets.py
.secrets/
secrets.env
credentials.json
api_keys.json
.scrapy/autothrottle.json
```
**What they are:** Files containing sensitive information:
- `config/secrets.py` — Python file with hardcoded API keys
- `credentials.json` — OAuth tokens or login credentials
- `api_keys.json` — API keys for retail websites (Amazon, Target, etc.)
- `secrets.env` — Environment file with all secrets

**Why ignore them:** 🔴 **CRITICAL SECURITY ISSUE** — If you commit these to GitHub:
1. Hackers can scrape public GitHub searching for API keys
2. Your retail scraping could be rate-limited or blocked
3. If you use payment APIs, your account could be charged by attackers
4. You'll need to immediately revoke and regenerate all keys

**For your project:** When you build the scraper, you'll need:
- API keys from retail websites
- Possibly database credentials
- User agent strings for web scraping

**Best practice:** Create `config/secrets.example.py`:
```python
# config/secrets.example.py (COMMIT THIS)
AMAZON_API_KEY = "YOUR_KEY_HERE"
TARGET_API_KEY = "YOUR_KEY_HERE"
SCRAPY_USER_AGENT = "Your-Bot-Name/1.0"
```

Then each developer creates `config/secrets.py` locally (in .gitignore):
```python
# config/secrets.py (NEVER COMMIT THIS)
AMAZON_API_KEY = "actual-secret-key-12345"
TARGET_API_KEY = "another-secret-key-67890"
```

---

### **13. Cached Scraping Data**
```
data/cache/
data/output/
```
**What they are:** Your application caches scraped products so it doesn't re-scrape every time. The `output/` folder stores results users export.

**Why ignore them:** These change during runtime and are huge (potentially 100s of MB). They're not source code.

**For your project:** When your scraper runs, it will store cached products here to avoid re-scraping. Don't commit these large data files.

## Summary: What Gets Committed vs. Ignored

| Category | Example | Commit? |
|----------|---------|---------|
| **Source Code** | `src/scrapers/amazon_scraper.py` | ✅ YES |
| **Configuration Template** | `config/secrets.example.py` | ✅ YES |
| **Requirements** | `requirements.txt` | ✅ YES |
| **Tests** | `tests/test_scrapers.py` | ✅ YES |
| **Documentation** | `docs/scraper_guide.md` | ✅ YES |
| **Secrets** | `config/secrets.py` | ❌ NO |
| **API Keys** | `api_keys.json` | ❌ NO |
| **Virtual Environment** | `venv/` or `.env` | ❌ NO |
| **IDE Settings** | `.vscode/`, `.idea/` | ❌ NO |
| **Compiled Files** | `__pycache__/`, `*.pyc` | ❌ NO |
| **Test Reports** | `htmlcov/`, `.coverage` | ❌ NO |
| **Cache Data** | `data/cache/`, `data/output/` | ❌ NO |

## How to Use This .gitignore

1. **It's already in your repo** — The `.gitignore` file is already committed to your repository.
2. **It applies to all new files** — Any files matching these patterns won't be staged by `git add .`
3. **Use `git status`** — Run this to see what will/won't be committed
4. **Create secrets template** — Create `config/secrets.example.py` with dummy values, commit it. Other developers copy it and add real values locally.

## Quick Start for Your Project

```bash
# 1. Clone the repo
git clone https://github.com/gitsalluk/local-product-finder.git
cd local-product-finder

# 2. Create virtual environment
python -m venv venv
source venv/bin/activate  # On Windows: venv\Scripts\activate

# 3. Copy secrets template
cp config/secrets.example.py config/secrets.py

# 4. Add YOUR secrets to config/secrets.py (THIS FILE IS IGNORED BY GIT)
nano config/secrets.py

# 5. Install dependencies
pip install -r requirements.txt

# 6. Run the program
python src/main.py
```

The `.gitignore` ensures that your `config/secrets.py` (with real API keys) never gets committed! ✅
